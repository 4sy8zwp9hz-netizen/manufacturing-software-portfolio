# Evidence and Ownership Standard

## What “verified” means

A capability is described as verified only when it was observable in current code,
configuration boundaries, tests, launcher/runtime assets, or version-control
history. The audit was used to establish facts; none of those private artifacts are
published here.

## Ownership language

Case studies separate personal engineering work from surrounding systems. “I
designed” or “I implemented” refers to the application and workflow work described
in the ownership matrix. Source databases, manufacturing processes, enterprise
email infrastructure, Windows administration, and upstream records are treated as
dependencies, not personal creations.

## Confidence labels

- **Verified:** directly supported by audited implementation or history.
- **Reconstructed:** a clean-room diagram or narrative derived from verified roles.
- **Illustrative:** fictional data or terminology used only to explain a concept.
- **Not claimed:** contextual infrastructure or business outcome that was not
  measurable from the repository.

## Claims deliberately avoided

This portfolio does not claim quantified savings, yield improvement, adoption,
uptime, or cycle-time reduction. Those outcomes require controlled operational
evidence that is not contained in source code. The case studies instead explain
the mechanism by which the software reduces search effort, duplicated queries,
manual transcription, or deployment friction.
